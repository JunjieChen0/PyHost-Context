## 0. 一句话定位

把课题从"再多扰动几个环境变量"收紧为：**发现 Python 测试中的隐式环境假设，并对"如何修复这些
假设而不削弱测试"给出可审计的评估**。可行性研究已经把"能测到差异"证完了；本研究要回答的是
差异**有多普遍、来自什么、修得掉吗、修完还测得出来吗**。

## 1. 贡献定位与新颖性边界

**潜在增量（本研究要交付的三件东西）**

1. **跨项目的受控测量**：同一固定软件栈、同一 9 条件设计、同一记账纪律，在 **30 个独立选取的
   项目**上测量隐式环境假设的影响范围，并给出项目层与类别层的比例及其区间。
2. **根因证据**：每个确认单位都给出最小复现、产品读数路径、测试假设与固定判定程序下的归类，
   而不是只报"翻红了几个测试"。
3. **保持测试语义的修复评估**：三种修复策略（全局固定 / 测试局部隔离 / 显式参数化）分别消除
   什么、保留或遗漏什么，并用**反静默变异探针**证明修复后测试对该行为仍然敏感。

**明确不主张的新颖性**：不是"Python ＋ 环境变量"。近邻已有：flake-exorcist 已做 TZ / locale /
哈希种子的扰动并区分环境依赖；ChaosAPI 已研究主动控制 API 行为来发现测试问题。本研究的增量
必须落在**跨项目测量 + 根因证据 + 语义保持的修复评估**上，其余一律作为对照或背景。

**本研究与可行性研究的关系**：可行性研究提供**方法**（三态启动环境、三视图证据、逐轮状态恢复、
进程组清理、E0—E4 等级、A1→B→A2 恢复块）与**仪器**（`matrix/tooling/`），并提供"这个现象确实存在"
的实例；本研究提供**知识**（普遍性、根因、修复）。两者分母严格分开。

## 2. 三个研究问题与判据

### RQ1 影响：哪些隐式环境假设会让测试结果变化，影响是否跨项目、跨类别出现？

- **单位**：`unit = 项目 × K 条件`（每项目 8 个）。主统计单位是**项目**，不是测试节点。
- **确认判据（先于执行固定，机械可判）**：一个 unit 为**确认差异**，当且仅当
  1. 该 unit 的扰动轮 5/5 各自同一（身份集合、失败签名、阶段三态跨轮一致），且 A 与 B 不同；
  2. 翻转节点集在 5 个扰动轮内**完全相同**；
  3. 该翻转节点集里的**任何一个节点，在 45 轮等预算 B0 对照中都没有翻转过**；
  4. 该 unit 的 session 完整、扰动有效、无超时。
- **报告量**：确认 unit 数 / 全部 unit 数；**至少一个确认 unit 的项目比例**（Wilson 95% 区间，
  n = 30）；按 5 个应用类别的比例（Clopper–Pearson 精确区间，n ≈ 6）；每项目翻转节点数与
  独立根因数（二者不得混同）。
- **噪声底**：等预算 B0 对照直接给出"固定环境下仅重复运行"的逐测试翻转率。判据 (3) 是本研究
  相对可行性研究的**收紧点**：把"五次一致"升级为"在 45 次固定环境重复中从未翻转"。

### RQ2 根因：变化来自产品功能问题、测试隔离不足、合理表示变化，还是证据不足？

每个确认 unit 必须产出四项证据，缺一项即不得进入 C1—C3：

- **(a) 最小复现**：最小的调用方式与确切的变量取值，能稳定复现翻转；
- **(b) 产品读数路径**：冻结版本里读取该变量或其取值的代码位置（`file:line`，含判定分支）；
- **(c) 测试假设**：测试依赖环境却未建立该前置条件的位置（`file:line`）与断言；
- **(d) 判定**，按下列固定程序，**首个成立的类别生效**：
  - **C1 产品功能问题**：产品在 B 下的行为**违反其自身文档化契约**，或与 B0 下的行为在同一
    功能语义上不一致，且能引用契约出处（文档 / 变更记录 / 官方 API 说明）。
  - **C3 合理表示变化**：差异**只**落在显示或排版表示上，两种表示都符合契约，且观察到的载荷
    中**不存在功能性差异**；测试对表示过度指定。
  - **C2 测试隔离不足**：产品行为符合契约，但测试断言了依赖环境的状态而未显式建立它。
  - **C4 证据不足**：(a)(b)(c) 不能全部建立，或 C1 与 C2/C3 的证据冲突且不可判；记 `unresolved`。
- **纪律**：`environment_sensitive` / `representation_change` 是**语义标签**，不等于根因；
  C4 不得被"向上取整"为任一确定类别。**33 个失败节点不等于 33 个缺陷**；独立根因数按
  "同一产品路径 + 同一测试假设 + 同一机制"合并计数。
- **可审计性**：全部证据从冻结工件与归档原始证据重算；抽样 **20%** 的 unit 由独立一方向
  **盲复分类**，报告原始一致率与不一致清单（双方都保留）。

### RQ3 修复：三种策略分别消除了什么，又保留或遗漏了什么？

对每个已归类的 unit，在**独立补丁分支**上分别实施三种策略（原始测量工件不变）：

| 策略 | 要回答的问题 |
|---|---|
| **R1 全局固定环境** | 是否只是让问题**不再出现**（环境被钉死，测试仍不表达自己的前置条件）？ |
| **R2 测试局部隔离** | 是否**明确建立**了该测试需要的前置条件，且不依赖会话级全局设置？ |
| **R3 显式环境参数化** | 是否**同时覆盖**了产品原本应支持的不同环境行为？ |

**修复判据（A、B、C 三条必须同时成立；D 单独报告）**

- **A 失败消失**：在 B 条件下，修复后的套件该 unit 的翻转集为空（并且 A1/A2 式复核仍一致）。
- **B 义务保留**：原断言义务未被削弱——被触碰的测试里**不得删除、跳过、xfail 或放宽任何断言**；
  修复后套件在 B0 下仍全部通过；对测试文件做机械 diff 检查，列出所有断言相关改动。
- **C 覆盖仍存（反静默变异探针）**：对**产品代码**施加一个最小、可逆的**行为变异**，该变异会破坏
  所讨论的行为；要求修复后的套件在变异下**失败**（B 与 B0 两个条件下都要失败）。
  三重矩阵必须全部符合：

  | 套件 | 产品 | 条件 | 期望 |
  |---|---|---|---|
  | 原始 | 原始 | B | **失败**（原观察） |
  | 修复 | 原始 | B | **通过**（判据 A） |
  | 修复 | **变异** | B 与 B0 | **失败**（判据 C：行为仍被覆盖） |

- **D 覆盖范围**：报告该策略是否覆盖产品原本应支持的其他取值（例如其它 `TERM` 值、其它宽度），
  以及是否遗漏了 B0 与 B 之外的第三种行为。R3 预期覆盖最广，R1 预期最窄——这是待检验的假设，
  不是预设结论。
- **纪律**："变绿"不算修复成功。任何以删除/弱化测试换来的绿色，按 B 判据直接记为失败并保留记录。

## 3. 样本：采样框、顺序、版本、准入、替补

**规模目标：30 个项目 = 探索组 20 + 独立验证组 10**，5 个应用类别各 6 个。
30 是**可执行的设计目标**，不是 CCF-B 的录用门槛。

### 3.1 采样框与顺序（事先固定）

- **框来源**：`top-pypi-packages-30-days.min.json`（BigQuery 下载量月度快照）。冻结文件按
  **SHA-256** 绑定；本研究使用 `last_update = 2026-10-01` 快照，`rows = 15,000`。
- **顺序**：按 `download_count` 降序的名次即选样顺序；**不做任何结果无关之外的调整**。
- **准入前纪律**：在样本选定**之前**，**不得**检查任何候选项目是否读取环境变量，**不得**按
  "看起来会读环境变量"筛选、排序或替换。主样本必须能解释**一般项目**中的影响范围。

### 3.2 版本规则（事先固定）

对每个候选：取该快照时点的**最新发布版本**；要求 (i) 存在 sdist，(ii) `requires_python` 允许
CPython 3.11（字段缺失记 `unspecified` 并按 3.11 处理，准入时验证）；(iii) sdist 与 wheel 的
SHA-256 记录进工件绑定表。**不得**为得到更"好看"的结果而更换版本。

### 3.3 准入条件（按固定次序施加，全部只使用元数据或 B0 基线）

按名次自上而下，逐条施加；任一条不满足即记 `excluded`＋原因，进入下一个候选：

| 编号 | 条件 | 判定方式 |
|---|---|---|
| A1 | 不在可行性样本内 | 与 8 个已用项目及其镜像/同名包比对 |
| A2 | 是"自带测试套件"的项目，而非元包/空壳 | sdist 内含测试文件 |
| A3 | 纯 Python，构建无需编译器 | 有 `py3-none-any` wheel；sdist 无 `.c/.pyx/.rs/.go` 与 `ext_modules` |
| A4 | sdist 体积 ≤ 15 MB | 元数据 |
| A5 | 该版本可装入冻结 venv 并成功 `uv pip check` | 准入执行 |
| A6 | 基线可收集：`pytest --collect-only` 成功且收集 ≥ 50 个测试 | 准入执行 |
| A7 | **B0 基线**单轮耗时 ≤ 60 s 且套件全程无外网需求、无外部服务 | 准入执行 |
| A8 | 起始源码树可由冻结 sdist 逐字节恢复（重复两次一致） | 准入执行 |

- **准入只能用 B0**。**扰动条件的结果不得影响样本构成**：A5—A8 的判定只允许读 B0 基线证据。
- **成本上限（预注册）**：全部 30 个选定项目在 A7 下的单轮基线耗时之和 × 45 × 2 若超过
  **60 小时**，则按**基线耗时降序**排除项目直至落入上限，**在跑任何扰动轮之前**执行并逐条记录。
- **替补规则**：某类别内的候选准入失败，取该类别**名次下一个**候选，最多替补 5 次；
  每次替补记录被替换者、替补者、原因。替补不得改变类别配额，也不得事后调整类别定义。

### 3.4 类别配额与归类规则（事先固定）

5 个类别，各 6 个：**CLI／时间与国际化／文本与配置／数据处理／开发测试工具**。

- 归类由**固定有序规则**决定，首个命中者生效；判定材料只用 (i) PyPI 主题分类器，再 (ii) 项目
  **名称**中的固定词表（名称是客观的，不随描述文字漂移）；词表与规则顺序在协议 JSON 中冻结并
  按 SHA-256 绑定。类别之间的平局按协议中固定的类别次序裁决。
- **归类在任何准入运行之前完成**，归类表整体哈希后冻结。

### 3.5 探索组与验证组的划分（事先固定）

在每个类别内，按名次把准入通过者排序：**前 4 个 → 探索组（5×4 = 20）**，
**其后 2 个 → 独立验证组（5×2 = 10）**。划分在任何扰动轮之前冻结。

**独立验证组的纪律**：在探索组完成分类与修复规则**之前**，**不得**分析验证组数据，也**不得**
用验证组调整分类规则、条件或判据。验证组只做一件事：检验探索组形成的规则是否成立。

## 4. 设计与对照

### 4.1 主矩阵（与可行性研究保持可比）

- **条件**：B0 + K01_TZ / K02_LC_ALL / K03_LANG / K04_HASH / K05_NO_COLOR / K06_TERM /
  K07_COLUMNS / K08_LINES，取值与三态模型完全沿用冻结协议，**不做任何调整**。
- **重复**：每 unit 5 次。
- **规模**：30 × 9 × 5 = **1,350** 次执行。
- 仪器、启动环境三态、三视图证据、逐轮状态恢复、进程组清理、网络规则、超时处理全部沿用
  `matrix/tooling/`，版本与承诺另记新批次。

### 4.2 等执行预算 B0 对照（本研究新增的关键对照）

- **规模**：30 × 45 = **1,350** 次 B0 执行（每项目在主打矩阵的 5 次之外，再加 40 次）。
- **作用**：(i) 给出**噪声底**——固定环境下仅重复运行的逐测试翻转率；(ii) 使 RQ1 判据 (3)
  可判；(iii) 回应"五次一致不能证明不存在低频不稳定"。
- **调度**：B0 对照轮与主矩阵轮**交错**执行（按冻结 seed 生成的交错调度），避免把机器漂移误读
  成环境效应；交错顺序在运行前冻结并哈希。
- **记账**：与主矩阵分开记账，但同属一个批次承诺。

### 4.3 工具对照：flake-exorcist

- **版本**：`flake-exorcist 0.1.0`（wheel `5ebf343e…`、sdist `3d4cea12…`），独立 venv，冻结
  解释器同版本。
- **比较范围（只比共同支持的变量）**：其 `ENVIRONMENT`（时区、locale）与 `SEED`（PYTHONHASHSEED）
  维度，对应本研究 K01 / K02 / K03 / K04。
- **单独披露**：它的 `ORDER` 与 `PARALLEL` 维度本研究**不覆盖**；本研究的 K05—K08
  （NO_COLOR、TERM、COLUMNS、LINES）它**不覆盖**。工具支持范围必须逐条披露，不得只报"通过率"。
- **记账**：工具自身派发的 pytest 进程**另列**预算行，不计入主矩阵执行数。

### 4.4 恢复复核

沿用 A1→B→A2、每合格单位最多 2 块、参照位于块内第 1、3 位、两批顺序为哈希序与严格反序。
上限 **288** 次，另列记账。

### 4.5 修复验证

每个已归类 unit：3 策略 × 4 次运行（原始+原始+B、修复+原始+B、修复+变异+B、修复+变异+B0）
= 12 次，上限 **480** 次，另列记账。补丁与变异各有 SHA-256，归档在修复分支记录里。

## 5. 统计单位、估计量与区间

- **主要单位**：**项目**（n = 30）。报告"至少一个确认 unit 的项目比例"，Wilson 95% 区间。
- **类别层**：5 类各 6 项目，用 Clopper–Pearson 精确区间；类别间只作描述性比较，不做多重比较
  显著性主张。
- **根因层**：独立根因数（合并规则见 RQ2）。报告根因分布、按类别的分布、以及**确认成本**
  （每个确认单位消耗的执行次数与机器时间）。
- **修复层**：按策略报告 A/B/C 三条判据的通过数与通过比例，D 覆盖范围逐条描述。
- **明确不做**：
  - 不把 5 次重复当统计功效依据（沿用既有说明：单次失败概率 0.10 时，5 次至少一次失败的概率
    为 0.40951）；
  - 不把测试节点数当独立发现数；
  - 不把"未观察到差异"写成"无作用"；未确认的 unit 全部保留在分母中。
- **低频不稳定**：由 45 轮 B0 对照给出可报告的翻转率，不用"5 次一致"承担"不存在 flaky"的任务。

## 6. 记账与预算

| 预算行 | 计算 | 上限 |
|---|---|---|
| 主矩阵 | 30 × 9 × 5 | 1,350 |
| 等预算 B0 对照 | 30 × 45 | 1,350 |
| 恢复复核 | 2 块 × 3 轮 × 合格单位 | 288 |
| 修复验证 | 12 × 已归类单位 | 480 |
| 工具对照（flake-exorcist） | 其自身派发 | ≤ 1,300 |
| **合计（不含工具对照）** | | **≤ 3,468** |

- **时间估算**：可行性研究实测 **8.88 s/轮**（270 轮 2,397 s）。按 30 个项目的准入基线均值
  保守取 10—20 s/轮，主矩阵＋B0 对照 2,700 轮约 **7.5—15 小时**纯执行时间；加恢复、修复与工具
  对照约 **12—22 小时**，加每轮准备与恢复开销按 1.5 倍计约 **18—33 小时**。落在 4—6 周窗口内
  可行，但**必须先完成准入耗时估算**再启动，成本上限规则见 A7。
- **账本纪律**（沿用）：执行前登记完整计划、每完成一轮落盘、`not_run_ids` 单一共享规则、
  计数永不从"成功返回条数"推断、批次自校验不过按中止处理。失败尝试与引航**另列**，不混入分母。

## 7. 停止与决策规则（用结果决定是否继续，而不是无限扩样）

**探索组完成后**（20 项目、主矩阵＋B0 对照完成），按下列门判断：

- **G1 跨项目重复机制**：至少 3 种不同根因机制各在 ≥ 2 个项目中出现，或至少 1 种机制在
  ≥ 4 个项目中出现。
- **G2 可审计修复**：至少 2 个 unit 在三种策略中至少一种上同时满足判据 A、B、C（变异探针通过）。
